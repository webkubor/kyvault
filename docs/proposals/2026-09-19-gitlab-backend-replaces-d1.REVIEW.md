# Review: GitLab 后端替代 D1 方案

- **对象**：`docs/proposals/2026-09-19-gitlab-backend-replaces-d1.md`
- **Reviewer**：Codex（`codex exec --sandbox read-only`，独立 child session）
- **日期**：2026-09-19
- **方式**：静态审查；未修改文件、未运行写入型测试、未验证 CortexOS 生产实现

## Verdict

**revise**

GitLab 作为 file 后端的同步方式可行，但当前方案不足以支撑 D1 退役：权限承接未明确、并发处理存在丢数据路径、初始化与迁移流程不完整。

## 关键问题（按严重度排序）

### P0-1：冲突工作区可能被当成空库，下次写入覆盖原有数据

方案第 108 行允许 rebase 冲突后交给用户处理；但 `rust/src/store.rs:107` 将读取失败或 JSON 解析失败统一视为空对象，`set_secret` 随后保存整个对象（205–241 行）。716–725 行的测试甚至明确确认"坏文件被新内容覆盖"。

若冲突标记进入实际 Store 的 `secrets.json`，一次 `set` 就可能把整库替换成单条记录。历史提交或许能恢复，但当前工作数据仍被覆盖。

**修订要求：** 冲突状态禁止读写正常库；只有文件确实不存在才允许初始化为空。同步应在隔离状态完成解析与结构校验，再更新可用快照。

### P0-2：退役计划没有证明现有权限边界能连续保留

方案第 100、136、142 行把删除 D1 与权限能力退役关联，却没有承接方案。`SKILL.md:256–265` 明确承诺越权 404、远程禁止写、本机放行。

同时，Rust 的 `rust/src/d1.rs:180` 直接按 ID 查询密文，没有身份或 visibility 条件；321–345 行也直接列出全部元数据。**这里保存策略字段，并不执行文档描述的授权边界。**仅凭删除 Rust D1 模块，不能断言 CortexOS 服务端能力也随之退役。

**修订要求：** 先明确 CLI、CortexOS 服务、D1 表分别由谁维护、在哪里鉴权。迁移前保持生产授权路径；不得把"窗口期无 visibility"作为默认过渡。

### P0-3：Git 的远端冲突检查不能阻止同一本地库丢更新

`rust/src/store.rs:205` 是无锁的整文件读改写；116–124 行还使用固定 `secrets.json.tmp`。两个本机 agent 从同一快照分别修改不同 secret，后写者可以覆盖先写者；固定临时文件也会竞争。

这种丢失发生在 commit 之前，push 仍可能完全符合 fast-forward。

**修订要求：** 为同一个 vault 增加跨进程事务锁，覆盖读取、修改、保存，以及会替换工作文件的同步操作。逐 secret 锁无法保护当前整文件写入。

### P1-1：团队初始化描述与代码行为不符，存储路径未闭合

方案第 52 行声称 `kyvault init` 生成"与团队共享的同源副本"；实际 `rust/src/store.rs:91` 生成独立随机 key，不会复制团队 key。

方案又把密钥放在 `~/.keyring/master.key`、仓库放在 `~/.keyring/_remote/`。现有 Store 将 `master.key` 与 `secrets.json` 固定在同一 root（53–59 行），不能直接表达这个布局。

**修订要求：** 明确首次建库与加入已有库两条流程，以及唯一活动文件、密钥来源和路径映射；不得覆盖已有个人 key。

### P1-2：强制退役却把迁移全部交给用户，无法兑现兼容承诺

方案第 41 行承诺保留现有能力，第 113 行要求用户自行迁移，第 136 行又固定删除 D1。现有 `annotate` 仅支持 D1（`main.rs:369–397`），file 的普通 `set` 不保留 D1 的业务元数据。

**修订要求：** 将新增 GitLab 与删除 D1 分成两个验收事项；提供一次性迁移路径，并明确哪些能力、字段必须由 CortexOS 承接。

## 决策点逐条意见

### 决策点 1：master.key 不入仓

- **判断：** 合理的责任划分，不是技术债；但"传输由用户负责"不能替代完整的加入团队流程。方案第 75–83 行要求另一个密码管理器或消息渠道，对普通开发者确有额外负担，应如实定位为"已有安全共享渠道的小团队方案"。
- **建议：** 保留带外分发，但修正第 52 行。管理员生成一次；成员导入同一个 key，验证能解开已有密文后才允许写入。`KEYRING_MASTER_KEY` 优先于文件（`store.rs:75–85`），也应纳入错误 key 的诊断。
- **边界：** 删除 GitLab 成员不能收回已下载的密文和 key；需要另行说明成员退出时的轮换责任。第 80 行"飞书加密消息"应明确具体机制，不能仅凭产品名称认定渠道安全。

### 决策点 2：Backend 中 GitLab 与 File / D1 并列

- **判断：** 枚举并列可以接受。它表达用户选择的运行模式，不必要求底层存储实现彼此独立。第 65 行已经通过 `local: Store` 表达复用关系。
- **建议：** 保留当前小规模枚举即可，CRUD 统一委托 Store，同步逻辑归 `GitLabRemote`，不要复制加密和序列化实现。
- **真正风险：** "同一 schema"不等于"同一份活动数据"。必须说明 `_remote/secrets.json` 是实际 Store 文件，还是 `~/.keyring/secrets.json` 的副本；若是副本，要定义同步失败时谁为准，否则重现第 24 行的"存过但找不到"。

### 决策点 3：visibility / 越权 404 退役

- **判断：** GitLab 不做 visibility 的范围选择合理；现有生产边界因此消失则不可接受。方案第 142 行把存储替换与授权退役混为一谈。
- **建议：** v2.3 至完成迁移验收前，CortexOS 继续使用原有 D1 授权路径。若最终由 CortexOS 承接策略，只能让可信服务持有全集与 master key，远程 agent 经该服务访问。
- **必要条件：** 若所有 agent 都拿到仓库全集和同一 master key，CortexOS 的应用层过滤可被绕过；这不是补一个过滤函数就能解决的。
- **文档命运：** `SKILL.md:232–278` 应明确标为 CortexOS 服务路径的能力，并与维护者协调迁移归属，不能按方案第 152 行直接整段删除。

### 决策点 4：并发使用 fast-forward / rebase

- **判断：** Git 足以承担远端提交竞争检测，但不提供"按 secret ID 合并"的保证。方案第 108 行把文本冲突等同于同一 secret 冲突，承诺过强。
- **不同 clone：** 两个 agent 修改不同 secret，文本改动互不重叠时可自动合并；相邻行、共同插入位置或 JSON 标点变化也可能造成不同 secret 的冲突。可以接受这种保守拒绝，但必须如实说明。
- **同一 clone：** 必须增加 vault 级跨进程锁；无需为了这个问题引入分布式逐 secret 锁。
- **建议：** 定义未提交改动如何处理、rebase 失败如何恢复、pull 后再次被别人抢先 push 如何返回。第 89 行在 push 时才 commit，而第 91 行 sync 先 pull，尚未说明 dirty worktree 的处理。
- **强推：** 第 109 行允许裸 `--force` 会破坏上述保护。建议不提供；如保留恢复入口，至少绑定预期远端提交，拒绝覆盖未见过的新提交。

### 决策点 5：不并网 D1 和 GitLab

- **判断：** 不做长期双写、双向同步合理；这不意味着不能提供一次性迁移工具。
- **建议：** 在删除 D1 之前提供独立迁移脚本或命令，采用明确的源和目标，在内存中解密并重加密，不经终端、argv 或明文临时文件。
- **最低迁移契约：** 目标冲突默认拒绝覆盖；逐条验证解密结果和记录集合；失败可恢复；切换前停写或使用一致快照；验收前保留原 D1。
- **元数据：** D1 的 `kind/account/org/scopes/visibility` 不能通过普通 file `set` 完整迁移（`d1.rs:325–344`、`store.rs:234–241`）。报告必须列出未承接字段；权限策略未落地的记录不能直接迁入所有成员可解密的共享库。

### 决策点 6：D1 退役是否先与 CortexOS 维护者对齐

- **判断：** 必须对齐。kyvault 可以决定新用户推荐路线，但不能单方面证明生产消费者已经具备替代路径。
- **建议：** 将 v2.6 改为"最早候选移除版本"，以 CortexOS 维护者确认、迁移完成、权限回归通过及回滚方案为删除门槛。
- **范围区分：** 分别列出 Rust CLI D1 适配器、CortexOS Go D1 客户端、数据库和服务端权限层。`d1.rs:1–11` 已明确存在跨项目共享契约，不能用一个"D1 退役"覆盖所有组件。
- **证据限制：** 当前方案没有提供跨项目对齐记录；本次也未读取 CortexOS 实现，不能宣称已完成对齐。

## 设计漏洞

- **仅排除 master.key，不足以防止共享个人凭据。**
  `main.rs:403–409` 将 D1 连接凭据存进默认 file 库。如果方案第 49、89 行同步的是该库全集，就可能把这些管理凭据也分享给团队。需要明确团队库与个人自举库的边界，以及首次同步的记录集合。

- **GitLab 仓库并非全部内容都加密。**
  `store.rs:234–240` 的平台和名称是明文 JSON 键，旧格式还可含明文元数据；第 3–7 行要求保留未知字段。因此方案第 49、126 行应准确写成"secret 值加密，名称、结构及部分元数据可见"，不能暗示整个文件都是密文。

- **"git log 自带审计"需要缩小承诺。**
  方案第 126 行最多证明提交历史；本地 `get/run` 不形成读取审计，显式 push 前的多次修改也未必逐次留痕。

- **迁移时间表内部不一致。**
  第 99 行已经要求 doctor 弃用警告，第 134 行又将其列为 v2.4 新行为。应统一时间，且警告不能把依赖权限边界的生产用户直接引向不等价替代品。

## 代码兼容性

| 检查项 | 结论 |
|---|---|
| `Backend::GitLab { local, remote }` | Rust 允许 tuple 变体与具名字段变体混用，语法兼容。风格统一为包装结构可选，不构成阻断。 |
| 分发修改范围 | 除 `main.rs:207–259` 的选择、CRUD、名称外，还必须处理 `main.rs:376` 的穷尽匹配，否则新增变体后无法编译。 |
| 后端选择 | 当前 `main.rs:214–221` 将所有非 `d1` 值视为 file。新增三态时应显式解析并拒绝未知值，避免配置错误静默落到个人库。 |
| 模块导出 | 在 `lib.rs` 增加 `pub mod gitlab;` 合理；还需导入类型并接入命令解析。仅增加枚举不构成功能实现。 |
| "22 个命令行为不变" | `main.rs:535/579/617/682/746` 等直接创建默认 Store，不经过 Backend。若 GitLab 使用独立 root，这些命令仍操作另一库；必须逐命令定义路由。D1 自举命令则应继续保持本地专用。 |

**加密兼容性：`crypto.rs` 可以不动，但必须指定复用 file 格式。**

`crypto.rs:3` 明确存在两套 wire format：

| 项目 | file / 拟议 GitLab | D1 |
|---|---|---|
| AES key | `SHA256(base64_decode(master.key))` | base64 解码后直接使用 |
| 密文封装 | 一个 base64 字符串，含 nonce 与带认证标签的密文 | nonce、带认证标签的密文分别 base64 |
| AAD | 空 | 空 |

因此，"都用 AES-256-GCM"本身有歧义；"GitLab CRUD 直接复用 Store，同步不重新加密"才明确。把 D1 的 master key 和密文列简单复制、拼接成 file 格式不能完成迁移，通常必须解密后按目标 file key 重加密。

**Git 依赖：没有 git 库并不冲突，但实现选择缺失。**

`Cargo.toml:17` 当前是 10 个直接运行依赖，另有 1 个开发依赖，不是 4 个；确实没有 git 库。

可以通过 `std::process::Command` 调用系统 Git，实现 clone、fetch、rebase、push，无需新增 Rust git 库。但方案必须明确：

- 系统 Git 是运行前提，缺失时如何诊断。
- SSH 认证、主机校验及无人值守失败行为。
- 使用独立参数传递，不拼 shell 命令。
- 冲突、超时、认证失败、远端拒绝分别如何恢复。

这些属于新增同步能力的必要契约，不能由"git 协议会处理"代替。

## 一句话总结

**可以新增 GitLab 同步，但应先补齐冲突与本地并发保护、团队 key 初始化和一次性迁移，再以 CortexOS 完成权限承接作为 D1 删除条件。**
